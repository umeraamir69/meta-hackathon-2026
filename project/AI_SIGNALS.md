# AI code signals — research and design

**Status:** proposal (Phase 1 specified, Phase 2 needs an eval gate before it ships)
**Date:** 2026-10-27 · **Owner:** Muhammad Umer Aamir
**Related:** `FEATURES.md` (gate + Muse contract), `src/muse.js` (call budget),
`src/rules.js` (deterministic patterns)

## 1. Problem

Agents now write a large share of routine PRs: dependency bumps, test
backfills, issue-to-PR loops. Teams want to know *which* PRs are
agent-written so they can review them differently — more skepticism toward
plausible-but-wrong code, extra attention to security-sensitive paths.
Stanford (2022) found developers with AI assistants wrote measurably less
secure code while feeling *more* confident; Veracode's multi-model
evaluation puts AI-generated code at 2.74× the vulnerability rate of
human-written code. Origin is a legitimate review input.

The request: catch agent-written PRs in PR Diff Sentinel.

## 2. What we will not do

Stylistic "AI or human?" guessing must never be a gate, and must never be
phrased as an accusation. The research consensus is blunt:

- IEEE S&P 2026: detectors miss the large majority of AI text in the worst
  cases; institutions should not trust them for verdicts.
- UMD ("Almost AI, Almost Human", 2025): detectors flag even lightly
  AI-polished writing as fully AI-generated.
- Practitioner reports (2026): clean, well-structured human code and prose
  is disproportionately flagged; paraphrasing/humanizer tools evade
  detection outright.

So this feature reports **signals, not proof**. A PR with no signals is not
"certified human"; a PR with signals is not "convicted". Every surface must
say that. Evasion is trivial (delete the trailer), which is fine: the goal
is review triage, not forensics.

## 3. Design: two layers

| Layer | Method | Reliability | Effect |
|-------|--------|-------------|--------|
| 1. Attribution signals | Deterministic matchers on trailers, authors, branches, artifacts, banners | High precision, low recall (only catches self-declared agent work) | Advisory; optionally strict |
| 2. Muse assessment | Spark verdict + Wonder review focus, grounded **only** in Layer-1 evidence + masked diff stats | As good as its citations; abstains when thin | Advisory, always |

Layer 2 never free-guesses from code style. If Layer 1 finds nothing, Layer 2
does not run — there is nothing honest to assess. This is the central
decision of this doc.

## 4. Layer 1 — deterministic attribution signals (Phase 1)

Severity `info`, flagged `advisory: true`. The gate ignores them unless
`SENTINEL_AI_STRICT=true`, which promotes them to `low` blockers.

| Rule | Where | Matches (examples) |
|------|-------|--------------------|
| `ai_trailer` | Commit messages, PR title/body | `Co-Authored-By:` + assistant name (Claude, Codex, Copilot, ChatGPT, Gemini, Cursor, Aider, Devin); `Generated-by:`, `Assisted-by:`; `ai-generated`, `generated with` |
| `ai_author` | Commit author/committer, PR author login | Agent-named bots (`copilot[bot]`, `claude[bot]`, `*-agent[bot]`) and assistant names; CI/dependency bots (`dependabot[bot]`, `github-actions[bot]`) excluded |
| `ai_branch` | PR head ref (hosted scan) | `copilot/…`, `codex/…`, `claude/…`, `devin/…`, `swe-agent/…` prefixes |
| `ai_artifact` | Tracked paths (tree, diff, staged) | `AGENTS.md`, `CLAUDE.md`, `.claude/`, `.codex/`, `.cursor/`, `.aider*`, `.ai/`, `.muserules` |
| `ai_banner` | File/diff content | `generated by <assistant>`, `co-authored-by: <assistant>` (assistant-name forms only, so the matcher cannot match its own source) |
| (PR metadata reuses the aspect rules above with source `pr-diff`, path `pull-request`) | Hosted scan only | PR author login, head branch ref, title + body scanned with the same matchers; one finding per matched aspect |

Notes:

- Assistant-name matching is case-insensitive. Bare `muse` is excluded:
  this product's own name would self-trigger.
- Content banners require an assistant name; bare `ai-generated` runs only
  on commit messages, never file content (docs *about* AI would drown us).
- `.sentinelignore` suppresses noisy signals with `rule ai_artifact` etc.,
  exactly like secret rules.
- Report shape: `advisory` count next to `count`; `ok` and exit code use
  blocking findings only. SARIF maps `info`/`low` to `note`. CI annotations
  use `::notice` for advisory, `::error` for blocking.

## 5. Layer 2 — Muse assessment (Phase 2, eval-gated)

### 5.1 Trigger and budget

Runs only when **all** hold: Layer 1 found ≥1 signal, a Model API key is
set, `SENTINEL_MUSE` is not `false`. Mirrors the existing secrets split:

| # | Model | Input | Output |
|---|-------|-------|--------|
| 1 | Spark (`muse-spark-1.3`) | Signal list + per-file +/- stats + trailers/authors + ≤N masked snippet lines | Verdict + evidence bullets + confidence |
| 2 | Wonder (`muse-wonder-1.0`) | Same, only when verdict is `likely_agent` or `mixed` | Review-focus notes (what to scrutinize, not a rewrite) |

Hard budget: at most 2 extra calls per scan, batched (one call per PR, never
per file). Same guards as secrets triage: `reasoning.effort: minimal`,
20s timeout, contributor-model refusal, JSON-shape validation, length caps,
credential-echo discard. Without a key, Layer 1 stands alone.

### 5.2 Draft prompts

Spark (verdict). Served with the signal table and masked stats:

```text
You assess whether a pull request shows signs of AI-agent authorship.
You do not decide anything about merging. You accuse no one.
Base the verdict ONLY on the listed signals and diff statistics below.
Stylistic hunches without a cited signal are forbidden: if the signals are
thin, reply "unclear" and say what is missing.
Never invent filenames, authors, or signal text. Never reproduce code.
Reply with JSON only:
{"verdict": "likely_agent|likely_human|mixed|unclear",
 "confidence": "high|medium|low",
 "evidence": [{"signal": string, "why": string}],
 "review_focus": [string]}
"likely_human" requires positive evidence (e.g. long author history on these
files plus zero signals); absence of signals alone means "unclear".
Keep every string under 280 characters.
```

Wonder (review focus, only for `likely_agent`/`mixed`):

```text
An agentic PR triage flagged this pull request as <verdict> with evidence
<evidence>. The deterministic secret gate already ran separately.
Write short review-focus notes for the human reviewer: which classes of
defect to scrutinize (auth, input handling, migrations, tests that assert
nothing), grounded in the changed paths below. Do not rewrite code. Do not
restate the verdict as fact; say "signals suggest".
Reply with JSON only: {"notes": [{"path": string, "focus": string}]}
```

### 5.3 Context and token budget

Per PR call, worst case: ~40 signal rows + file stats (~30 lines) +
≤60 masked snippet lines + prompt (~400 tokens) ≈ **3–5k input tokens**,
≤800 output tokens. Published API pricing at time of writing: Wonder
$4/$20 per 1M in/out; Spark materially cheaper (Spark Open listed at
$1.25/$4.15 — confirm on Billing, figures move). At those rates a fully
assessed PR costs on the order of **a few cents**, and PRs without Layer-1
signals cost **zero** (Layer 2 never runs). Monthly bounding: assessment
runs only on PR scans (Action, site, extension, local-app PR mode), never
on the pre-commit hook or scheduled history sweeps.

### 5.4 Reliability, abstention, eval

- **Abstention policy:** `unclear` is a first-class verdict. The prompt
  demands it when evidence is thin, and the renderer shows "unclear" without
  any warning color.
- **Wording:** surfaces say "signals consistent with agent authorship",
  never "AI-generated". The PR comment links this doc.
- **Eval plan (ship gate for Phase 2):** build a labeled set of ~50 PRs —
  known agent PRs (repos that disclose bot authorship; `copilot/` branches;
  disclosed challenge sets) vs known human PRs (pre-2023 history, maintainer
  PRs with discussion). Measure verdict accuracy and abstention rate with
  Muse *off* vs *on*. Ship Layer 2 verdicts only if `likely_agent` precision
  ≥ 0.9 on the set with recall reported honestly; otherwise keep Layer 1
  only and revisit. Adversarial note: all Layer-1 signals are removable in
  seconds, so recall has a hard ceiling by design.
- **Bias guard:** eval set must include non-native-English authors and terse
  human styles; a verdict pattern that tracks prose fluency instead of
  signals fails the gate.

### 5.5 Eval datasets available (checked 2026-10-28)

- **AIDev** (Li et al., MSR 2026 Mining Challenge) — 932,791
  agent-authored PRs from Codex, Devin, Copilot, Cursor, and Claude Code
  across 116k repos, plus a curated 33,596-PR subset from 2,807 repos with
  >100 stars (comments, reviews, issues included). Mined via account names,
  branch prefixes, and co-author trailers — the same signals as §4.
- **AIDev + matched human baseline** ("Not All Agents Are Equal") —
  37,623 provenance-labeled PRs plus human PRs from the same repos and
  window (Dec 2024 – Jul 2025). This is the recommended primary set: both
  classes, PR-level, real repos.
- **GitHub-Agentic-PR-Dataset** (HuggingFace,
  `mabujadallah/GitHub-Agentic-PR-Dataset`, CC-BY-4.0) — 39.5M PRs
  (~1.96M agent) with commits and file diffs. Deeper backup if AIDev
  access stalls.
- **GPTSniffer** (HuggingFace, `mahirlabibdihan/GPTSniffer`) —
  snippet-level human-vs-ChatGPT pairs. Weaker fit (snippets, not PRs;
  single older model; published baselines only reach 70–78%), useful at
  most as a secondary sanity check — and as further evidence that
  stylistic verdicts stay advisory-only.

Methodology warning: AIDev labels come from attribution signals, so
Layer-1 "recall" on AIDev would be circular (near-perfect by
construction — do not claim it). Use AIDev for (a) Layer-1 precision on
the human baseline (must be ~zero false fires), (b) Layer-2 verdict
quality and abstention rate on both classes, (c) end-to-end UX review.
Sample ~100 PRs per class; the full sets are far larger than we need.

### 5.6 Train vs use (decision: use, do not train)

Use Muse Spark/Wonder through the Model API with the §5.2 prompts. Do not
train a classifier, for four reasons:

1. **Circularity (decisive).** AIDev labels come from attribution signals,
   so a supervised model trained on it mostly relearns trailer/branch
   regexes — which Layer 1 already implements exactly. Training buys
   nothing there, and the leftover stylistic signal is where published
   baselines stall at 70–78% (GPTSniffer family).
2. **Serving.** There is nowhere to host weights: the surfaces are a
   serverless function, a composite Action, a CLI, and a browser
   extension. An API call fits all four; a model file fits none.
3. **Calendar.** Training + data plumbing + eval + serving does not fit a
   Nov 4 submission. Prompting + eval does.
4. **Event fit.** This hackathon rewards building *with* Meta's models.
   A well-evaluated Muse pipeline beats a half-trained classifier on all
   three Indie criteria (creativity, ambition, works).

Revisit only if all three change: a non-attribution-derived labeled set,
a serving story, and time. Fine-tuning on the Model API is not announced;
even if it appears, point 1 still applies.

## 6. Privacy and safety

- Same pipeline as secrets: masked snippets only, `scrubFindings` before
  any model call, key-echo discard on the way back.
- No author profiling beyond repo metadata already in the diff (name,
  trailers, branch). No cross-repo identity joins.
- Nothing is stored: the Action and site keep no per-author history. Note in
  the privacy section of the site before shipping Phase 2.
- Strict mode is explicit (`SENTINEL_AI_STRICT=true` / Action
  `ai_strict: 'true'`), default off, and documented as "block on
  self-declared agent work" — never as proof of it.

## 7. Surfaces

| Surface | Change |
|---------|--------|
| CLI JSON | `advisory` count; advisory findings inline with `advisory: true`; `assessment` object when Layer 2 runs |
| PR comment | `### AI signals` section (advisory list + verdict + link to this doc); header stays PASS unless secrets fail |
| Report page / local app | Same section; stats row gains an advisory count |
| Site + extension | Advisory count + compact list; extension shows one summary line |
| SARIF | Included as `note` results with rule ids above |

## 8. Rollout — robust implementation plan

Each step lists files, tests, and a done-criterion. Nothing lands with the
suite red or the self-scans dirty. Order is dependency-sorted; effort in
focused sessions.

### Phase 1 — deterministic signals + advisory plumbing (done 2026-10-28)

**1a. Matchers — new `project/src/ai.js`.**
Content-banner regexes (assistant-name forms only), message patterns
(trailers + phrases), author/bot patterns, artifact glob list (reuse
`matchGlob` from `ignore.js`), PR-metadata helper. Pure functions,
no I/O, no secrets in source.
*Done when:* `project/test/ai.test.js` covers every matcher with
dynamically built fixtures (no literal that self-triggers), plus
negatives (human trailers, `api_key: process.env.X`-style near-misses).

**1b. Scanner wiring — `project/src/scan.js`.**
Banners in `scanText` (files, patches, decoded layers); artifact checks in
`scanWorkingTree`/`scanPatch`; author check per history chunk in
`scanGitHistory`; message patterns when `path === 'commit-message'`.
Findings carry `severity: 'info'`, `advisory: true`, masked non-secret
descriptors, fingerprints over rule+location (never values).
*Done when:* temp-repo tests show a bot-authored commit, an `AGENTS.md`,
and a bannered file each produce exactly one advisory finding, and the
`tool working tree is clean` self-scan still passes.

**1c. Gate semantics — `project/src/cli.js`.**
`ok`/`count`/exit use blocking findings only; report gains `advisory`
count. `SENTINEL_AI_STRICT=true` promotes advisory hits to `low`
blockers (single conversion point, documented).
*Done when:* advisory-only fixture → exit 0 with `advisory ≥ 1`; same
fixture under strict → exit 1; existing CLI tests unmodified and green.

**1d. Surfaces.**
`annotate.js` (`::notice` for advisory), `comment.js` (`### AI signals`
section; header stays PASS without secrets), `report-html.js` (section +
stat), `web/lib/remote-scan.js` (PR author/branch/body signals,
passthrough of `advisory` + flags), `web/components/scanner.js`
(compact section), `extension/popup.js` (one summary line),
`action.yml` (`ai_strict` input), then `node scripts/sync-sentinel.mjs`
from `web/` to re-vendor (`ai.js` joins the file list).
*Done when:* each surface renders an advisory-only scan without
failure styling, and `sync --check` passes.

**1e. Verification.**
Full suite green; root self-scan clean (tree *and* history — old commit
messages get scanned too); `demo-history.mjs` output unchanged; web
`next build` green; extension headless harness green.
*Done when:* all of the above in one clean run, then commit + push.

### Phase 2 — Muse assessment (after Phase 1, eval-gated)

**2a. Prompts + plumbing — `project/src/muse.js` (or new `assess.js`).**
Spark verdict call + Wonder review-focus call per §5.2, triggered only
when Layer 1 fired and a key is set. Same guards as secrets triage
(minimal reasoning, timeout, contributor refusal, JSON validation,
length caps, echo discard). Report gains `assessment` object; local
fallback = Layer 1 list with "Muse off" note.
*Done when:* mocked-fetch tests cover verdict parse, `unclear`
abstention, invalid-JSON fallback, key-echo discard, and no-call when
Layer 1 is empty or the key is missing.

**2b. Surfaces.** Comment verdict block + doc link, report section, web
and extension verdict lines. Wording per §5.4 ("signals suggest").
*Done when:* advisory-only scan with a mocked `likely_agent` verdict
renders correctly on all four surfaces.

**2c. Eval harness — new `project/eval/ai-signals.mjs` + results file.**
Samples ~100 agent + ~100 human PRs (§5.5 sets), runs Layer 1 and (with
key) Layer 2, scores precision-on-humans, verdict accuracy, abstention
rate. Results recorded under `project/eval/results/` with date + model
ids. No training, no weight files, ever.
*Done when:* harness runs end-to-end and numbers are written down,
whatever they are.

**2d. Ship gate.** Verdicts ship only at `likely_agent` precision ≥ 0.9
with the bias checks from §5.4 passing. Otherwise Layer 1 ships alone
and this doc records the miss honestly.
*Done when:* a go/no-go line is added to this section with the measured
numbers.

Also in Phase 2: one-paragraph privacy note on the site (nothing stored,
§6) before any hosted verdict goes live.

### Phase 3 — polish (only if Phases 1–2 land early)

Preset bundles (e.g. strictness aliases), per-path signal stats on the
report page, demo-video segment (bot PR → advisory → strict block).

### Risks and mitigations

| Risk | Mitigation |
|------|------------|
| Self-scan noise (docs *about* AI tripping banners) | Assistant-name-only content rules; advisory never fails; verify root + history scans in 1e |
| Prompt-injection via PR text into Layer 2 | Evidence-only grounding rules; JSON validation; echo discard; caps |
| Cost surprise | Layer 2 gated on Layer-1 hits; per-PR batching; §5.3 math reviewed before enablement |
| Accusation harm from a wrong verdict | Advisory-only, "signals suggest" wording, abstention default, eval gate, doc link on every verdict |
